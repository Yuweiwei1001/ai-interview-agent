## 2. 遇到的问题与解决方案全录

### 2.1 编排与状态管理

**P1 面试在编程题后直接终结，候选人感知"没有进入下一题"**
- 现象：多场面试跑完编程题就结束，轮次远少于预期。
- 根因：早期文本评分用长度启发式 `answer.length()*2`，长回答恒定满分，触发"连续 3 轮达标提前结束"特性——**失真的指标驱动了错误的流程决策**。
- 解决：① 移除提前结束特性；② 文本评分改用 `AnswerEvaluator` LLM 真实评分（失败降级参考分 60）；③ maxRounds 改由计划 `estimatedTotalRounds` 决定（此前恒为 20，计划形同虚设）。
- 面试表述："我发现流程异常的根因在评估指标失真，所以先修指标、再下线依赖失真指标的流程特性；这件事也促使我后来建了 golden set 评测做回归门禁。"

**P2 LLM 编程题路由失控：出"Redis 限流器"进代码编辑器 / 一直不出编程题**
- 现象：系统设计题被塞进 Monaco 编辑器；或 LLM 始终不路由 coding，编程环节被跳过。
- 根因：把**控制流决策**交给 LLM，存在幻觉且不可复现。
- 解决：CoordinatorNode 确定性护栏五件套：全场最多 1 道编程题；至少先 2 轮非编程题；主题强制算法池（数组/链表/哈希/栈队列/二叉树/双指针/排序二分/DP）；第 3 轮起未出过则强制路由；CodingAgent 偏移检测（命中 Redis/Kafka/分布式等关键词→加强约束重试一次→仍偏移用算法题库兜底）。
- 面试表述："LLM 只负责内容生成，控制流走确定性规则——这是本项目与 ReAct 自主循环方案的本质区别，也是评测指标可稳定度量的前提。"

**P3 实际出题与面试计划毫无关系**
- 现象：计划写了"Java 并发/Redis 分布式锁"，实际出的却是泛化题。
- 排查：通过可观测性 `llm_trace` 的 prompt 全文确认 CoordinatorNode 从未读 `state.getPlan()`，topics 走硬编码通用池。
- 根因：计划透传只做了持久化，**下游节点没有真正消费计划**。
- 解决：`pickTopic()` 按主轮消费索引顺序消费 `plan.agentAssignments[agent].topics`（无计划才回退池）；difficulty 用计划分配难度归一化；`weakPointPriority` + 历史记忆薄弱点合并注入出题 prompt。
- 验证：trace prompt 出现"考察主题：Java并发编程与Redis分布式锁原理"（topics[0]）。
- 面试表述："计划生效不能只看持久化 JSON，要验证到 prompt 层；我们靠 LLM 观测台的 trace 全文定位的。"

**P4 刷新页面/进程重启后，编程题等待状态丢失**
- 现象：图执行在内存中，一旦中断，"等代码提交"的现场无法恢复。
- 解决：StateGraph `interruptBefore("codingWait","codingRetryWait")` + `MysqlSaver` 按 `threadId=sessionId` 落 checkpoint；提交代码后 `resumeInterview` 加载 checkpoint 续跑；checkpoint 反序列化 `InterviewState` 可能变 `Map`，用 Jackson `convertValue` 兜底；`recursionLimit(50)` 防无限循环。
- 面试表述："这是 LangGraph 式 Human-in-the-Loop：挂起点前持久化，恢复时以 sessionId 为线程 ID 续图，和'保存业务状态再重跑'相比，图语义完整保留。"

**P5 挂起原因在外层感知不到（waitingForCode 设置位置踩坑）**
- 现象：`codingRetryWait` 挂起后，外层 handleGraphResult 不知道是"首次等代码"还是"重试等代码"。
- 根因：把 `waitingForCode=true` 写在**条件边**里，条件边不参与 checkpoint 状态体。
- 解决：挂起标志必须在 **EvaluateNode 节点体内**设置（06 决策 3），条件边只读状态做路由。
- 面试表述："状态图的'决策'和'副作用'要分离：条件边纯函数只路由，状态变更收口在节点体，否则持久化与外部感知会不一致。"

**P6 候选人长时间不答，图线程永久阻塞；迟到的回答可能错配给后续轮次**
- 现象：`AskQuestionTool` 用 `CompletableFuture.get()` 阻塞等回答，无超时则线程池（4 核 8 线程）会被耗光。
- 解决：`future.get(30 分钟可配)` 超时 → 发 `ANSWER_TIMEOUT` → `endInterviewOnTimeout`（置 interrupted、已有轮次生成报告、发 COMPLETE、关 SSE）→ 抛 `InterviewTimeoutException` 中断图；**超时即清理 pendingQuestions**，迟到回答因 future 已不存在被拒绝，不会错配。
- 面试表述："阻塞等待必须有超时收尾，且收尾要'状态一致'：会话状态、报告、SSE、等待队列四处一起处理，不能只抛异常。"

### 2.2 SSE 与前端交互

**P7 编程题提交后前端卡在"评估中"（最经典的端到端 bug）**
- 现象：后端评估已完成，前端永远等不到结果。
- 根因：SSE 发送时若无活跃连接，事件被**静默吞掉**且无日志；前端只信 SSE 单通道。
- 解决：三保险——① 发送失败必须移除死连接并留日志（丢事件留痕）；② 后端持久化 `current_question` 到 session 表（V5 迁移）；③ 前端 4~5s REST 轮询兜底（waiting_code 跳编码页 / completed 展示报告 / currentQuestion 变化补消息）。
- 面试表述："实时通道只优化体验，不承载正确性；关键状态必须可查询，轮询是兜底不是主力。"

**P8 长面试中 SSE 被容器/代理空闲断连**
- 现象：面试 20 分钟后流中断，或 Spring 抛 `AsyncRequestTimeoutException`。
- 解决：emitter 超时设 2 小时；守护线程每 15s 发注释帧心跳 `:ping` 保活；onCompletion/onTimeout/onError 统一清理注册表；前端 `connectGet()` 指数退避重连（1s→16s，最多 5 次），服务器主动 complete 不重连；重连入口 `GET /{id}/stream`。
- 面试表述："心跳解决空闲断连，重连解决真断连，轮询解决重连窗口期丢事件——三层各管一段。"

**P9 Spring MVC SSE 事件格式与前端解析不匹配**
- 现象：POST 流式响应解析错乱（`\r\n`、多行 data、半包）。
- 解决：前端 `parseStream()` 用 ReadableStream 读 buffer，按 `\n\n` 切事件、兼容 `\r\n`、多行 data 拼接；`connect()`（POST 启动）不自动重连防重复建会话，`connectGet()` 才重连。
- 面试表述："SSE 规范细节（事件分隔、data 多行、CRLF）必须自己兜底解析，不能假设服务端输出永远规整。"

**P10 报告页空白 / 回顾态异常**
- 现象：进入报告页空白；回顾历史会话时计时器还在跑。
- 根因：计划未透传复用、数据未就绪即渲染；回顾模式误挂实时态逻辑。
- 解决：报告页空白守卫（数据未就绪给占位而非白屏）+ 计划透传复用；回顾模式去计时器、UI 切回顾态。
- 面试表述："异步数据页面要有'未就绪/空/错误'三态设计，白屏等于把后端时序问题暴露给用户。"

**P11 编程页点"运行"界面零变化，用户感知"运行没用"**
- 现象：无预设用例走直接执行分支时，后端丢弃沙箱 stdout 只回 `results:[]`，前端停在占位文案。
- 解决：`TestRunResult` 携带 stdout 透传；前端空态区分"未运行"与"已运行无用例"；运行结束无测试结果自动切控制台 tab（展示 stdout 或编译错误）。
- 面试表述："运行反馈闭环：成功要看得见输出，失败要看得见原因，'没反应'是最差的反馈。"

**P12 无头浏览器自动化验证时 Monaco 编辑器空白**
- 现象：浏览器子代理截图编辑器区域空白。
- 根因：无头环境缺 GPU 渲染能力，Monaco 的环境限制。
- 结论：非代码 bug，不在此浪费排查时间；真实浏览器正常。
- 面试表述（若被问自动化测试）："要会区分环境限制与产品缺陷，避免在不可控因素上空转。"

### 2.3 LLM 调用、成本与可观测性

> **通俗解读简历第 4 条亮点「LLM 容错与成本治理」**：整场面试依赖 30+ 次 LLM API 调用，而 API 是外部、不可靠、按量付费的依赖，所以要解决两件事。**容错**＝给每次调用装安全气囊：60s 超时防拖死、1 次重试救抖动、仍失败就用预置规则兜底（出题→内置题库、评分→参考分 60、用例→空列表不造假），模型全挂面试也不中断，且 `degraded=true` 诚实告知；代码收口在 `LlmCallWrapper`，全仓禁止裸调。**成本治理**＝两板斧省钱：① 模型分层——"下一题派哪个面试官"这种简单决策用便宜快速的 qwen-turbo，出题/评分等质量任务才用 qwen-max；② Prompt 瘦身——观测台按 agent 归因发现出题 prompt 每轮注入全量简历（~2K token），而八股/算法题的简历无增益，移除注入（项目题保留），每轮省 ~2K token；合计单场降约 40%。方法论：先测量后优化、砍完验证语义无损。亮点末尾的 SSE 双通道是同思路用在交互层：网络也不可靠，SSE 主链路 + REST 轮询兜底。类比：连锁餐厅主厨缺席→等一等（重试）→SOP 手册出菜（规则兜底）→告示告知（诚实降级）；Routine 审批交实习生、重要方案交专家（模型分层）。

**P13 所有 LLM 调用报 400**
- 现象：`The value of the enable_thinking parameter is restricted to True`。
- 根因：qwen3.7-max 是混合思考模型，DashScope 强制 `enable_thinking=true`。
- 解决：application.yml 配 `enable-thinking: true`；写入开发规范防再犯。
- 面试表述："模型层的硬约束要在配置层显式声明并文档化，而不是靠人记。"

**P14 LLM 不可用时面试中断**
- 现象：DashScope 抖动/限流时，出题或评分抛异常打断整场面试。
- 解决：`LlmCallWrapper` 统一 60s 超时 + 1 次重试（1s 退避）+ 降级兜底；8 类调用点降级矩阵（计划→规则计划、路由→轮换决策、出题→内置题库、评分→参考分 60、追问→跳过/模板、摘要→截断 500 字、用例→空列表、代码评估→规则降级）；降级标记 `degraded=true` 诚实告知。
- 面试表述："AI 系统的可用性 = 主链路不被模型绑架；每个 LLM 调用点都要回答'失败了怎么办'。"

**P15 单场推理成本高（单场 30+ 次调用）**
- 排查：观测台按 agent 拆分 token，发现出题 prompt 每轮注入全量简历（~2K token 冗余）。
- 根因：① 全模型用 max；② 八股/算法题注入全量简历无增益（主题已由计划+Coordinator 保证）。
- 解决：模型分层（Coordinator 路由用 qwen-turbo）；Technical/CodingAgent 移除全量简历注入（ProjectAgent 保留，挖项目细节依赖它）；合计单场成本降约 40%。
- 验证：trace 全文确认 technical prompt 不再含"候选人简历"。
- 面试表述："成本优化先测量后动手——观测归因告诉你 token 花在哪，再决定砍哪；砍完要验证语义无损。"

**P16 llm_trace 归因缺失 / 轮次串联错乱（跨线程 ThreadLocal 三连坑）**
- 现象：trace 行 session/agent 为空；同轮出题与评分拿到不同 traceId。
- 根因：① `LlmCallWrapper` 每次新建单线程 executor，ThreadLocal 丢；② StateGraph 节点跑在图自己的线程池；③ `withTraceContext` 在节点体执行前用旧 state 设置上下文，CoordinatorNode 生成新 `roundTraceId` 后不刷新则本节点出题/检索拿上一轮 ID。
- 解决：wrapper submit 前捕获 `LlmTraceContext` 快照、执行线程内 set/finally clear（收口唯一）；所有节点包 `withTraceContext` 从 `InterviewState` 取 sessionId；CoordinatorNode 生成 `rt-*` 后**立即刷新当前线程上下文**。
- 面试表述："ThreadLocal 在三种线程模型下都会丢：临时 executor、框架线程池、'先设置后变更'的时序坑——解法是快照传播 + 状态源重建 + 变更即刷新。"

**P17 trace 只存 500 字摘录，排障看不全 prompt**
- 解决：`prompt-excerpt-length` 默认 -1 存全文，12000 字硬上限仅防 TEXT 列写失败；想控表体积可配置正整数。
- 面试表述："观测数据的截断策略要可配置，默认值服务排障场景。"

**P18 计划生成"重复调用"被质疑浪费**
- 现象：观测台看到 plan 两次调用。
- 根因：PlanGenerator 校验 `agentAssignments` 为空抛异常 → wrapper 正常重试，两次均真实消耗 token。
- 结论：属容错机制正常行为；重试各自成行、诚实计费（不做去重美化）。
- 面试表述："重试成本是真实消耗，观测要诚实；要优化的是校验前移，而不是账面上抹平。"

**P19 LLM 结构化输出反序列化失败，静默走兜底计划**
- 现象：计划频繁落兜底，LLM 能力没用上。
- 根因：`AgentAssignment.topics` 用 String 接收，LLM 恒返回数组 → Jackson 失败。
- 解决：`List<String>` 接收；prompt 拼接用字符串而非 `.text()` 模板（JSON 花括号冲突，probe 验证过的坑）；解析失败**主动抛异常**走重试而非吞掉。
- 面试表述："结构化输出三层策略：prompt 约束 + 防御性解析 + 业务兜底；失败要发声（抛异常进重试），静默降级会掩盖模型层问题。"

### 2.4 沙箱与代码评测

**P20 用户提交的不可信代码直接在宿主机跑的风险**
- 解决：Docker 硬隔离——`--network none`、`--read-only`、`--memory 512m`、`--cpus 1`、`--pids-limit 64`、30s 超时 `destroyForcibly`；编译期安全黑名单（`Runtime.exec`/`ProcessBuilder`/反射/`Socket`/文件流/`System.exit`）；编译目录读写挂载、运行目录只读挂载；并发 max=3 超限拒绝；镜像启动预热。
- 面试表述："安全是纵深防御：网络/文件系统/资源/进程数/API 黑名单/超时，任何一层被突破还有下一层。"

**P21 默认模板点"运行"必然编译失败**
- 现象：`class Main is public, should be declared in a file named Main.java`。
- 根因：沙箱硬编码写 `Solution.java`，前端模板却是 `class Main`。
- 解决：前端默认模板 `public class Solution`、文件标签 `Solution.java`/`solution.py`，与沙箱约定对齐；写入开发约定"改模板必对照沙箱"。
- 面试表述："跨端硬编码约定要有'契约测试'思维：任何一端改动都要对照另一端。"

**P22 AI 动态用例解析失败时注入假用例，拉低真实分数**
- 现象：LLM 用例 JSON 解析失败若造占位用例，正确代码反而判不通过。
- 解决：解析失败/LLM 不可用**返回空列表，不造假用例**；三级保障：预设用例 → AI 动态边界用例 → 内置模板兜底（覆盖"两数之和"系列），保证正确代码真实跑沙箱。
- 面试表述："降级可以'少评'，不能'错评'；造假数据比缺失数据危害更大。"

**P23 评估链路异常时误导候选人反复改正确代码**
- 解决：`degraded=true` 时重试提示改为"评估服务暂不可用，代码本身可能没有问题"；异常链路给中性分 40，替代长度启发式。
- 面试表述："降级文案是产品决策不是文案决策——错误提示会直接驱动用户行为。"

**P24 评测驱动卡死 12 分钟：第二次代码提交永不触发**
- 现象：coding 重试路径下，EvalRunner 等"状态离开 waiting_code"永远等不到。
- 根因：重试路径状态**持续保持** `waiting_code`（题目也可能不变），任何"状态离开才重置"的驱动标志都失效。
- 解决：以 `coding_submission` **DB 计数为事实来源**决定提交第几份代码；驱动复刻 `CodingSubmitController` 落库链路（`resumeCoding` 内部不写提交记录，不补写计数恒 0）；预置代码耗尽主动 `endInterview`。
- 面试表述："驱动外部系统时，标志位要用'单调递增的事实'（DB 计数），不要用'会反复进入的状态'。"

**P25 重试同题导致轮次/重复率统计失真**
- 解决：规则指标主轮按题面归一化去重（coding 重试产生同题多条记录）；追问率/达成率均基于去重后主轮。
- 面试表述："指标口径要先定义'统计单位'，重试场景下同题多条记录是最典型的口径陷阱。"

### 2.5 长期记忆与人格策略

**P26 关键词粗匹配记忆不准（"Java"这种粗粒度词无法指导出题）**
- 现象：旧实现按关键词黑名单抽 topic，记忆全是粗词，薄弱点注入无意义。
- 解决（Mem0 轻量改造）：① `AnswerEvaluator` 评分同次调用提取 1-4 个**具体概念**（如"HashMap扩容机制"，≤30 字，最多 4 个）；② EvaluateNode 优先 LLM 提取、空才降级关键词兜底；③ `KnowledgePointService` UPDATE 语义加权融合：`mergedConfidence=(old×count+score)/(count+1)`，"上次薄弱这次答好"逐步修正旧结论；④ 三阶段归一化（精确匹配→相似度≥0.85 最长公共子串→新建）防同义 topic 分裂；⑤ CoordinatorNode 注入 top5 薄弱点定向追问。
- 验证：两场完整面试确认提取具体、融合正确、薄弱点触发定向题。
- 面试表述："记忆系统的价值在'可消费的粒度'——粗词无法注入 prompt 指导出题；UPDATE 语义保证记忆随证据演化而非被最新一次覆盖。"

**P27 压力型人格"不追问"/追问被做成放水**
- 现象：早期追问策略与人格脱节，压力型失败不追问，或追问变成给提示。
- 解决：追问统一 `ON_FAILURE`（答得好 ≥60 不追问，像真实面试官）；追问是施压/引导手段：压力型不重试不提示但照常追问，语气按人格区分（压迫式/引导式/中性）；编程题达标阈值按严格度（STRICT 80/STANDARD 60/LENIENT 40）、重试上限按人格（0/2/1）。
- 面试表述："人格不是文案皮肤，是一组决策参数（严格度/重试/提示/追问）的策略对象——BehaviorPolicy 接口四个决策点、三种实现。"

### 2.6 环境、依赖与工程

**P28 MySQL 时间显示差 8 小时**
- 解决：docker-compose 给 MySQL 容器配 `TZ=Asia/Shanghai`。

**P29 Windows 下 Maven repackage 静默失败**
- 现象：打包"成功"但 jar 未更新，启动还是旧代码。
- 根因：运行中的 java 进程锁定 jar 文件，Windows 文件锁导致 repackage 静默失败。
- 解决：先停旧进程再打包；排查时对比 jar 时间戳。
- 面试表述："构建'成功'不等于产物更新，Windows 文件锁是典型静默失败源，要验产物不验日志。"

**P30 引入 actuator 后启动报 "required a bean of type HttpSecurity"**
- 根因：`spring-boot-starter-actuator` 激活 `ManagementWebSecurityAutoConfiguration`，而项目关了 Security 自动配置。
- 解决：`spring.autoconfigure.exclude` 同步排除两个自动配置，只保留 `BCryptPasswordEncoder`。
- 面试表述："引入 starter 要审查它传递的自动配置——为启用 Spring AI Observation 埋点引 actuator，副作用是安全自动配置。"

**P31 中文 query 检索英文知识库文档无结果**
- 根因：跨语言相似度低于 `similarityThreshold=0.5`。
- 结论：知识库语言应与面试方向语言一致；该阈值同时是"宁缺毋滥"的护栏（检索无结果返回 null 不阻断面试）。

**P32 前端 vite.config.ts 报 process 类型错误**
- 解决：修复 `tsconfig.node.json` 的 types/lib 配置，让 node 环境类型对 vite 配置生效。

## 3. 高频面试追问 Q&A（深问防御）

**Q1 为什么不用 function calling / Agent SDK（LangGraph Platform、OpenAI Agents SDK）？**
答：本项目是**确定性业务流程**，需要图挂起等代码提交、SSE 流式出题、评分降级这类深度定制；SDK 的自主循环不可精确控制轮次/成本/prompt，难调试且有厂商锁定。全仓无 `@Tool`，LLM 只做内容生成不做行动决策（AskQuestionTool 只是普通 Bean）。副作用是 trace 天然没有 tool span——这是架构决定的，不是遗漏。

**Q2 沙箱通过率为什么只占 20% 权重？**
答：用例覆盖度有限——用例全过不代表代码好（上限靠 LLM 主观评价），但用例挂了基本一定有问题（下限靠沙箱）。沙箱是"下限保障"而非"上限评判"。权重：correctness 0.35 / codeQuality 0.20 / edgeCase 0.15 / timeComplexity 0.10 / testPassRate 0.20。

**Q3 挂起/恢复具体怎么实现？**
答：`interruptBefore("codingWait","codingRetryWait")` → 图执行到挂起点前 checkpoint 落 MySQL（MysqlSaver，threadId=sessionId）→ 线程返回；提交代码后 `resumeInterview` 以同 threadId 加载 checkpoint、注入代码到 `currentAnswer` 续跑。恢复时 `InterviewState` 可能被反序列化为 Map，Jackson `convertValue` 兜底。

**Q4 如何抑制幻觉？（分层答）**
答：① 编排层：控制流走确定性 StateGraph + 编程题护栏，LLM 无路由权；② 事实层：RAG 出题/评分双注入 Top-3 片段作评分事实依据；③ 决策层：追问/重试由规则门控（≥60 不追问），LLM 只生成措辞；④ 输出层：结构化三层策略，解析失败重试/降级不造假；⑤ 验证层：golden set + LLM-as-Judge + 人工校准回归。

**Q5 SSE 丢事件怎么办？并发能力多少？**
答：丢事件三保险（留痕/`current_question` 持久化/轮询兜底）+ 心跳保活 + 指数退避重连。并发：`interviewExecutor` 4 核 8 线程（每场占 1 线程，8 路并发会话）；向量化池 core2/max8/queue100 CallerRuns；沙箱池 max3；观测异步单线程 + 有界队列 1000（满丢弃仅 warn，观测故障绝不影响主链路）。

**Q6 评测体系怎么保证 Judge 自己可靠？**
答：三层指标分离——规则指标（确定性门禁：轮次达成/目标达成/跑题数/重复率/覆盖率/降级率）不依赖 LLM；LLM-as-Judge 只评质量维度（出题-JD 相关性、追问针对性），失败标 degraded 不伪造分数；`JudgeCalibrator` 用人工标注 golden QA 验证 AnswerEvaluator 档位一致率，过低即调评分 prompt。"编排正确性"与"生成质量"分开评估，避免模型能力与系统能力混为一谈。

**Q7 Context 窗口怎么管理？**
答：token 粗估（中文 1/字、英文 1/4 字符）；≤6000 完整历史；6000~8000 滑窗（最近 3 轮完整 + 更早 LLM 摘要 ~200 token/轮）；>8000 硬裁剪（仅最近 1 轮）。当前仅 Coordinator 决策使用。

**Q8 题目去重怎么做？**
答：`QuestionDeduper` Jaccard 相似度；Coordinator 出题重复时重新生成最多 3 次；topic 与已考察主题重复时替换为"综合技术"。

**Q9 JWT 双 Token 怎么做的？**
答：access 2h / refresh 7d，BCrypt 密码；`JwtTokenInterceptor` 校验 Bearer/type=access/过期，userId 写 ThreadLocal（`BaseContext`，afterCompletion 清除）；前端 401 自动 refresh 重放。**异步面试线程需手动恢复 BaseContext**（经典 ThreadLocal 坑，同 P16）。

**Q10 为什么选 ES 做向量库？**
答：Spring AI `ElasticsearchVectorStore` 开箱即用（1024 维 + metadata 过滤 `kbId==n`），团队已有 ES 运维经验；检索 `similarityThreshold=0.5` + topK=3。已知局限：无 rerank、阈值不自适应（未来方向）。

**Q11 系统有哪些局限？重做会怎么改？（诚实加分题）**
答：无熔断器（持续故障仍先重试一次）；重试不区分错误类型（429 应退避、400 重试无意义）；LlmCallWrapper 每次新建 executor 有线程开销；沙箱 Docker CLI 进程级调用无容器池（首包慢）；观测无图节点级 span 树/TTFT；报告 PDF 实为 TXT；Redis 仅容器就绪未启用。这些都在 06 未来方向表里——**我知道边界在哪，比假装完美更可信**。

## 5. 面试表述原则

1. **STAR 结构**：现象（Situation/Task）→ 排查（Action，强调"用观测/trace/日志定位"而非猜）→ 方案（分层）→ 结果（量化 + 验证方式）。
2. **先风险后方案**：每个亮点先讲"不这么做会出什么问题"（幻觉/超卖/丢事件/误导候选人），方案才有说服力。
3. **主动说局限**：Q11 的缺口清单是"工程成熟度"证据——知道边界、有演进路线，比完美叙事可信。
4. **数字口径一致**：简历、本文、03/06 三处数字必须一致（本表为准）；被追问"40% 怎么算的"时答：turbo 替代 max 的路由调用 + 每轮 ~2K token 瘦身，按 DashScope 单价估算，观测台可复算。
5. **不会的诚实降级**：被问未实现能力（rerank、熔断器、容器池），答"现状 + 为什么当前够用 + 演进方案"，不编造。
