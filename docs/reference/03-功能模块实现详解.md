## 1. 认证模块（auth）

- **注册**：用户名唯一校验 → BCrypt 加密存库 → 返回双 Token。
- **登录**：`findActiveByUsername` + `BCryptPasswordEncoder.matches` → 返回双 Token。
- **刷新**：解析 refresh token → 校验 `type == "refresh"` → 重新签发双 Token。
- **JWT 拦截器**（`JwtTokenInterceptor`）：拦截 `/api/**`，放行 `/auth/**`；校验 `Bearer` 头、`type == "access"`、过期时间；成功后把 userId 写入 `BaseContext`（ThreadLocal），`afterCompletion` 清除。**注意**：异步面试线程需要手动 `BaseContext.setCurrentId(userId)` 恢复上下文（见 InterviewService）。
- 前端 `utils/request.ts`：axios 拦截器，401 时用 refresh token 刷新后重放请求。

## 2. 简历模块（resume）

- `POST /api/resumes/upload`：类型白名单（PDF/DOCX/DOC/TXT）+ 大小 ≤10MB → `TikaTextParser`（Apache Tika `parseToString`）提取纯文本 → SHA-256 内容哈希 → 存 `resume` 表（raw_text 全文）。
- CRUD：列表 / 详情 / 删除均校验 `user_id` 归属。

## 3. JD 模块（jd）

- 简单的 `title + raw_text` 文本 CRUD，用于面试计划生成时注入职位描述。

## 4. 面试计划引擎（plan）

- [PlanGenerator.java](../src/main/java/com/interview/agent/interview/plan/PlanGenerator.java)：prompt 注入简历原文 + JD + 方向 + 人格 + 时长 + **历史知识点摘要**（长期记忆读取）→ `chatClient.call().entity(InterviewPlan.class)` 结构化输出。
- 计划结构：`overallStrategy`、`agentAssignments`（technical/project/coding 各自的 topics/difficulty/estimatedRounds）、`weakPointPriority`、`estimatedTotalRounds`。
- 硬性规则：coding 固定 1 轮；总轮次按时长约每 5 分钟 1 题（5-8 之间）；technical 与 project 均分剩余。
- **失败降级**：LLM 不可用时返回规则兜底计划（同规则计算轮次分配）。
- **坑**：`AgentAssignment.topics` 必须用 `List<String>` 接收——LLM 结构化输出恒返回数组，用 String 会反序列化失败走兜底计划。

## 5. 多 Agent 文字面试流程（interview 核心链路）

1. `POST /api/interviews/start` → 创建 session（status=in_progress）+ 注册 SSE + 推送 `CONNECTED`；
2. 异步线程（`interviewExecutor`，4 核 8 线程）内：构建 `InterviewState` → 生成计划（回填 `interview_plan`）→ `graphBuilder.executeInterview(initialState)`；
3. 图内：`plan → coordinator → ask → evaluate → (followUp | coordinator) → ... → END`，每轮通过 SSE 与候选人交互（见 02 文档第 2 节）；
4. 图返回后：若 `waitingForCode` → 更新状态 `waiting_code` + 推送 `WAITING_CODE`（挂起流程，见本文第 9 节）；
5. 否则：`saveRounds` 整体重建轮次（`RoundPersistenceService.rebuildRounds`，先删后插保证最终一致）→ 计算平均分 → 状态 `completed` → **同步**生成报告（保证 `REPORT_READY` 先于 `COMPLETE` 推送）→ 推送 `COMPLETE` + complete SSE。
6. 异常路径：`InterviewTerminatedException` → 保持 interrupted 不推 ERROR；其他异常 → 状态 `interrupted` + 推 `ERROR`。

## 6. 行为策略（人格，policy）

[BehaviorPolicy](../src/main/java/com/interview/agent/interview/policy/BehaviorPolicy.java) 接口定义四个决策点，三种实现由 `BehaviorPolicyFactory` 按 persona 装配（默认 neutral）：

| 维度 | 压力型 Pressure | 温和型 Gentle | 中性型 Neutral |
|:---|:---|:---|:---|
| 评分严格度 | STRICT（基础分 **-15**） | LENIENT（基础分 **+15**） | STANDARD（不变） |
| 是否允许重试 | 否 | 是 | 仅 round ≤ 1 且 <60 分时一次 |
| 是否给提示 | 否 | 是（<60 分给三段式引导） | 否 |
| 追问策略 | ON_FAILURE（压迫式语气） | ON_FAILURE（引导式语气） | ON_FAILURE（中性语气） |

- 编程题联动：达标阈值按严格度（STRICT 80 / STANDARD 60 / LENIENT 40）；重试上限按人格（pressure 0 / gentle 2 / neutral 1），见 EvaluateNode.decideCodingRetry。
- 追问策略 `ON_FAILURE`：答得好（≥60 分）不点评不追问，直接进入下一题，像真实面试官；追问语气按人格区分（FollowUpGenerator.toneOf）——追问是施压/引导手段而非放水，压力型不重试不提示但照常追问。
- **追问决策的分层设计**：“是否追问”不是由单一 LLM 黑盒决定，而是三层分工：① 事实层——`AnswerEvaluator`（LLM）只输出分数/点评/知识点；② 门控层——`FollowUpGenerator` 内按 `policy.followUpStrategy()` + 分数阈值做**确定性 Java 规则判断**（`ON_FAILURE` 下 ≥60 直接返回空串，不产生 LLM 调用）；③ 措辞层——确认要追问后才调 LLM 生成追问话术（失败降级模板文案）。理由：控制流决策交给 LLM 有幻觉/循环风险且不可复现；人格策略（NEVER/ALWAYS/ON_FAILURE）是有限枚举规则，用规则表达零成本；门控确定才能让评测指标（追问触发率等）稳定度量——即“评分 agent 提供事实，编排层规则决定动作，生成 agent 只负责措辞”。

## 7. 长期记忆（memory）

- **写入**：EvaluateNode 每轮评估完成后调用 `KnowledgePointService.updateFromEvaluation(knowledgePoints, evaluation)`。知识点**优先取 LLM 评分时并发提取的 1-4 个具体概念**（AnswerEvaluator，如"HashMap扩容机制"，≤30 字、最多 4 个）；LLM 未输出时降级为关键词匹配兜底（粗粒度，不作主路径）。经 `KnowledgePointNormalizer` 三阶段归一化后 upsert（`UNIQUE(user_id, topic)`）：① 精确匹配（去空格标点小写）→ ② 相似度 ≥0.85（最长公共子串实现，预留 embedding 接入点）→ ③ 新建。置信度采用 Mem0 风格加权融合 UPDATE 语义：`mergedConfidence=(oldConfidence×count+newScore)/(count+1)`，status 按融合后置信度 ≥60 记为 mastered/weak（"上次薄弱、这次答好"会逐步修正旧结论，而非被最新一次覆盖），`verified=false`（管理端审核预留字段）。
- **读取**：PlanGenerator 计划生成时注入 `buildKnowledgeSummary()`（薄弱点 + 掌握点列表）。

## 8. 知识库 RAG（knowledge）★

对齐 ThinkVerse 的知识库能力：面试官维护私有知识库，启动面试时可选挂载；出题与评分环节自动检索注入。

### 8.1 管理链路（KnowledgeService + KnowledgeBaseController）

- 知识库 CRUD（`/api/knowledge-bases`）：按 `user_id` 归属隔离；删除知识库时**先删 ES 向量再删记录**（FilterExpressionBuilder 按 kbId 过滤，query="*" topK=1000 批量删）。
- 文档 CRUD（`/api/knowledge-bases/{kbId}/documents`）：`vectorize` 参数控制建库即向量化（VECTORIZING）还是暂存草稿（DRAFT）；更新/删除文档时同步清理旧向量。
- **异步向量化**（`vectorizeAsync`，移植 ThinkVerse）：`ConcurrentHashMap<docId, Object>` 文档级锁防重复；守卫检查（存在性/归属/状态）→ 删旧向量 → `splitAndEmbed` → 回填 ACTIVE（含 chunkCount）或 FAILED。
- **切分嵌入**：`TokenTextSplitter(800, 100, 5, 10000, true)` 切分；每个 chunk 携带 metadata（kbId/docId/title/chunkIndex）供过滤检索；线程池 core=2/max=8/queue=100/CallerRunsPolicy（`VectorizationExecutorConfig`）。
- **向量存储**：`ElasticsearchVectorStore.builder(restClient, embeddingModel).options(dimensions=1024).initializeSchema(true)`（`VectorStoreConfig`），索引 `spring-ai-document-index`；嵌入模型 text-embedding-v3。

### 8.2 面试检索注入（确定性预注入，非 LLM 工具调用）

kbId 传递链：`InterviewStartDTO.knowledgeBaseId` → `InterviewSession.knowledge_base_id`（V6）→ `InterviewState.knowledgeBaseId` → 节点；启动时 `InterviewService` 校验知识库归属。

| 注入点 | 检索 query | 用途 |
|:---|:---|:---|
| CoordinatorNode 出题（technical/project，coding 不注入） | 本轮 topic | 注入出题 prompt：“参考资料（来自面试官知识库）…相关则围绕其出题，不相关则忽略，不暴露参考资料存在” |
| EvaluateNode 评分（仅文本题） | 题目 + 回答前 200 字（`buildEvalQuery`） | 注入 AnswerEvaluator 作为评分事实依据 |

- `KnowledgeRetriever.search(kbId, query, topK=3)`：`similarityThreshold=0.5` + `filterExpression("kbId == n")`；格式化为【title】+ 正文（截断 500 字）；无结果/异常返回 null（不阻断面试）。**坑**：中文 query 检索英文文档相似度会低于阈值无结果，知识库语言应与面试方向语言一致。

## 9. 编程题模块（coding）★

### 9.1 挂起/恢复机制（面试模式）

1. CoordinatorNode 路由到 coding → `waitingForCode=true` → 条件边指向 `codingWait`，`interruptBefore("codingWait")` 生效，**图挂起**，checkpoint 已落库；InterviewService 检测到 `waitingForCode` → 更新状态 `waiting_code` + 推送 `WAITING_CODE`（携带题目）；
2. 前端跳转 CodingRoom（Monaco 编辑器），候选人编写代码；
3. `POST /api/coding/submit/{sessionId}` → 校验会话存在且 `waiting_code` 状态 + 归属校验 → 保存 `coding_submission`（round_number = 已有轮次数+1）→ 状态改回 `in_progress` → 推 `CODE_SUBMITTED` → **异步** `interviewService.resumeCoding(sessionId, code, language)`；
4. `resumeCoding` → `graphBuilder.resumeInterview(sessionId, code, language)`：加载 checkpoint（`RunnableConfig.builder().threadId(sessionId).resume()`），把代码注入 `currentAnswer`/`currentLanguage` 后 `invoke` 继续 → 从 `codingWait` 执行 → `evaluate`；
5. 评估后 `decideCodingRetry`：不达标且有重试机会（按人格上限）→ `waitingForCode=true` + `codingHint` → 再次挂起 `codingRetryWait` → 前端收到 `WAITING_CODE` 提示可修改重交；不达标且无机会 → 直接切题（`codingRetryWait` 不经过）；达标 → 继续后续轮次；
6. `handleGraphResult` 处理恢复结果：再次挂起 → 推 `WAITING_CODE`；完成 → 同第 5 节第 5 步。

**防误导设计**：评估链路异常（沙箱/LLM 不可用，`degraded=true`）时，重试提示改为"评估服务暂不可用，代码本身可能没有问题"（EvaluateNode），避免候选人反复修改本来正确的代码；异常链路给中性分 40（不再用长度启发式）。

### 9.2 Docker 沙箱（sandbox）

[SandboxService.java](../src/main/java/com/interview/agent/coding/sandbox/SandboxService.java) 通过 Docker CLI 执行：

- **Java**：写 `Solution.java` → 编译（`javac`，工作目录**读写**挂载）→ 运行（`java -cp /workspace Solution`，工作目录**只读**挂载 `:ro`）。
- **Python**：直接 `python /workspace/solution.py`（只读挂载）。
- **硬隔离参数**：`--network none`、`--memory 512m`、`--cpus 1`、`--pids-limit 64`、`--read-only`、`-i`（stdin 注入测试输入）、30s 超时 `destroyForcibly`。
- **代码安全黑名单**：`Runtime.getRuntime().exec`、`ProcessBuilder`、`java.lang.reflect`、`Class.forName`、`Socket`、`FileOutputStream/InputStream`、`Files.write`、`System.exit` 等编译期拒绝（`checkSecurity`）。
- **镜像预热**：`DockerSandboxExecutor` 启动时异步 `docker pull` 预热 `eclipse-temurin:21-jdk-alpine` 与 `python:3.12-slim`；并发控制：线程池（core 1/max 3，队列 10），`maxConcurrent=3` 超限直接拒绝。

### 9.3 测试用例引擎（testcase）

`TestCaseService.runWithDynamicTests` 三级保障：

1. **预设用例**：随题 JSON 下发，逐一沙箱执行比对输出；
2. **AI 动态用例**：`TestCaseGenerator` 把题目 + 代码 + 预设用例通过情况给默认 ChatClient（qwen3.7-max）→ 生成 3-5 个边界用例 → 跑第二遍；解析失败/LLM 不可用返回空列表（**不注入假用例**，避免拉低真实分数）；
3. **内置模板兜底**：动态用例与预设均空时，按题目关键词匹配内置用例（当前覆盖"两数之和"系列），保证正确代码真实跑沙箱、不被误判为未通过。

### 9.4 代码多维评估（CodeEvaluationEngine）

| 维度 | 权重 | 来源 |
|:---|:---|:---|
| correctness 正确性 | 0.35 | LLM |
| codeQuality 代码质量 | 0.20 | LLM |
| edgeCaseHandling 边界处理 | 0.15 | LLM |
| timeComplexity 时间复杂度 | 0.10 | LLM |
| testPassRate 测试通过率 | 0.20 | **沙箱客观指标** |

- LLM 不可用时整体走 `ruleBasedEvaluate`（以测试通过率为核心的规则评分，`degraded=true`）。
- 练习模式（非面试）：`POST /api/coding/run`（运行；无预设用例时直接执行沙箱并透传 stdout，前端控制台展示）、`POST /api/coding/submit`（跑用例 + 多维评估）。

## 10. 面试报告（report）

- `ReportGenerator.buildReport`：逐题反馈（题号/题目/回答/分数/点评）→ 总分（平均）→ 维度分（按 agent 分组：technical/project/coding/communication）→ 优势/不足/建议（规则化文案 + 维度阈值）→ **成长对比**（`GrowthComparator` 取该用户历史最近一场有分面试，计算 improvement）。
- 报告 JSON 存 `interview_session.report`，SSE 推送 `REPORT_READY`（data 为报告 JSON）。
- 手动结束面试也会生成报告（已有轮次数据），避免前端"报告生成中"无限等待；无轮次数据则跳过。
- `GET /api/interviews/sessions/{id}/report.pdf`：当前实现为 **TXT 文本导出**（`text/plain` 附件），非真实 PDF（计划中预留 OpenPDF 升级）。

## 11. SSE 实时通信（sse）

[SseRegistry.java](../src/main/java/com/interview/agent/sse/SseRegistry.java)：

- `ConcurrentHashMap<sessionId, SseEmitter>`；注册时先 complete 旧连接（重连替换）；onCompletion/onTimeout/onError 均移除注册。
- 连接超时 **2 小时**（覆盖长面试）；后台守护线程每 **15 秒发送注释帧心跳**（`:ping`），防止容器/代理空闲断连与 Spring `AsyncRequestTimeoutException`，发送失败即清理死连接。
- 发送失败（IOException / IllegalStateException）时移除连接并留日志——**无活跃连接时事件被丢弃必须留痕**（否则前端永久等待，如编程题提交后收不到结果）。
- 前端重连入口：`GET /api/interviews/{id}/stream`（面试中途刷新页面/编码页监听复用）；面试间 `POST /start` 流断开且 sessionId 已建立后自动切换该通道**指数退避重连**（1s→16s，最多 5 次），断连期丢失的事件由 5s REST 轮询兜底补偿（currentQuestion / status / waiting_code）。

## 12. LLM 容错统一封装（common/ai）

[LlmCallWrapper.java](../src/main/java/com/interview/agent/common/ai/LlmCallWrapper.java)：

- 统一 `callWithRetry(callable, fallback)` / `callWithRetry(agent, callable, fallback, timeoutSeconds, maxRetries)`：单线程执行 + **60s 超时** + **1 次重试**（1s 退避）+ **降级兜底**；另有 `callEntity` 别名。带 `agent` 参数的重载把归因名（plan/technical/project/coding/evaluator/followup/summarizer/testcase/code-eval）写入观测上下文（见第 15 节）。
- 全链路降级矩阵：

| 调用点 | 降级行为 |
|:---|:---|
| PlanGenerator | 规则兜底计划 |
| CoordinatorAgent | 轮换决策（agents 按 round%3，反循环强制切换） |
| Technical/Project/CodingAgent | 内置题库 |
| AnswerEvaluator | 参考分 60 |
| FollowUpGenerator | 跳过追问 / 默认追问文案 |
| ConversationSummarizer | 直接截断 500 字 |
| TestCaseGenerator | 返回空列表（走模板兜底） |
| CodeEvaluationEngine | 规则降级评估（degraded） |

- **非 LLM 故障点的容错**：

| 故障点 | 处理方式 |
|:---|:---|
| 题目重复 | CoordinatorNode 重新生成最多 3 次（QuestionDeduper） |
| 历史记忆读取失败 | 降级为无记忆模式，不阻断编排 |
| 候选人超时未答 | `AskQuestionTool` 阻塞等待（默认 30 分钟，`interview.answer-timeout-minutes` 可配）后发送 `ANSWER_TIMEOUT`，调用 `endInterviewOnTimeout` 自动收尾（取消等待、状态置 interrupted、已有轮次则生成报告、发 COMPLETE 并关闭 SSE），迟到回答因等待已取消而被拒绝、不会错配 |
| 手动结束面试 | `cancel()` 标记 terminated + `InterviewTerminatedException` 终止图，保持 interrupted 状态 |
| 观测写库失败 | 异步单线程 + 有界队列，满则丢弃、异常仅 warn——观测故障绝不影响主链路 |
| 知识点写入失败 | EvaluateNode catch 后仅 warn，不阻断面试 |
| REST 层异常 | GlobalExceptionHandler 统一兜底 |

- **已知缺口（演进方向）**：无熔断器（下游持续故障时每轮仍先重试一次再降级）；重试不区分错误类型（429 限流值得退避重试、400 参数错误重试无意义）；`LlmCallWrapper` 每次调用新建单线程 executor，高并发有线程开销（可换共享池 + `orTimeout`）；评分降级分 60 属“保流程”取舍，会轻微污染评估数据。

## 13. Context 窗口管理

[ContextWindowManager.java](../src/main/java/com/interview/agent/interview/agent/ContextWindowManager.java)：

- token 粗估：中文 1 token/字，英文 1 token/4 字符；
- ≤6000：完整历史；6000~8000：滑窗（保留最近 3 轮完整 + 更早轮次 LLM 摘要，~200 token/轮）；>8000：硬性裁剪（仅最近 1 轮）；
- 当前仅 CoordinatorNode 决策时使用（`buildCompressedHistory`）。

## 14. 评测体系（eval）★

端到端评测：用 golden 用例驱动真实面试链路，用确定性规则指标做回归门禁 + LLM-as-Judge 评质量维度 + 人工标注校准评分器。

### 14.1 用例数据集（EvalDatasetLoader）

- 数据位于 `resources/eval/dataset/*.json`（当前 case-01-good / case-02-poor）：简历文本 / JD / 方向 / 人格 / 时长 / **answerLevel**（GOOD/MEDIUM/POOR 回答脚本档位）/ 编程题提交序列（首个可为故意错误代码以触发重试路径）/ 驱动超时。
- 人工标注校准样本：`resources/eval/calibration/calibration-set.json`（题目+回答+预期档位）。

### 14.2 驱动与编排（EvalRunner + EvalService）

- **进程内驱动，不依赖 SSE/HTTP**：注入评测简历/JD 记录 → 以预置 sessionId（`eval-{caseId}-{ts}`）调 `InterviewService.startInterview` → 轮询 `current_question` 按 answerLevel 脚本提交回答 → `waiting_code` 时提交预置代码 → 终态/超时后收集全部轮次与时间线事件作为 `EvalTrace`。
- **代码提交以 DB 计数为事实来源（核心设计）**：重试路径下状态会持续保持 `waiting_code`（题目也可能不变），驱动若依赖“状态离开才重置”的标志会永远不触发第二次提交（曾导致评测卡死）。改为读 `coding_submission` 已有记录数决定提交第几份代码；提交时复刻 `CodingSubmitController` 完整链路（先 insert `coding_submission` + 状态改回 in_progress，再 `resumeCoding`）——因为 `resumeCoding` 内部不写提交记录，不补写会导致计数恒为 0 且轨迹缺提交记录；预置代码耗尽后主动调 `endInterview` 结束。
- **EvalService**：单线程 daemon 线程池串行跑用例（避免挤占面试线程池）；runId 查询进度（RUNNING/DONE/FAILED）；报告 JSON 同步写入 `./eval-reports/{runId}.json` 供版本间回归对比留档。
- 依赖评测专用账号（默认 `testuser`，需已注册）。

### 14.3 指标（metrics）

| 维度 | 实现 | 说明 |
|:---|:---|:---|
| 规则指标 | RuleMetricsEvaluator | 确定性、可复现：轮次达成率、goalAchieved（completed 且达成率≥0.8 且编程题恰好 1 道）、编程题跑题数（护栏有效性）、题目重复率、计划主题覆盖率、评估降级率、超时未回答数 |
| LLM-as-Judge | LlmJudgeEvaluator | 出题-JD 相关性 + 追问针对性（0-10 分/题）；judge 失败标记 degraded 不伪造分数（诚实降级） |
| Judge 校准 | JudgeCalibrator | 用人工标注 golden QA 验证 AnswerEvaluator 评分落入预期档位：精确/宽松一致率，过低说明评分 prompt 需调整 |

- 指标细节：主轮按题面归一化去重（coding 重试会产生同题多条轮次记录，重复题检测/达成率/追问率均基于去重后主轮）；主题覆盖率按 agent 分组判定（仅与该 agent 自己的轮次比对），轮次达预估数则视为已覆盖（兼容“系统设计”等泛化主题），题面+评分知识点的关键词命中过半即算覆盖。
- 汇总 Aggregate：完成率 / 目标达成率 / 平均达成度 / 重复率 / 覆盖率 / 跑题总数 / 降级率 / 平均相关性 / 平均追问质量。
- `skipLlmJudge` 可只跑规则指标（快且不耗 LLM）；`runCalibration` 随行校准。

### 14.4 前端评测页（EvalView）

- 路由 `/eval`（首页导航栏「Agent 评测」+ 快捷卡片双入口）：
  - **用例区**：`GET /api/eval/cases` 展示 golden 用例（档位徽标/方向/时长/提交数），可勾选子集；开关：跳过 LLM-Judge / 随行校准 → `POST /api/eval/run` 发起；
  - **运行中**：每 5s 轮询 `GET /api/eval/runs/{runId}`；支持 `?runId=xxx` 直链查看运行中/历史 run（可从日志/REST 拿到 runId 后直接分享）；
  - **报告**：汇总指标卡片（完成率/目标达成/轮次达成/主题覆盖/重复率/跑题数/Judge 两项评分）+ 校准对照表（预期档位 vs 实际分/严格宽松一致）+ 逐用例卡片（规则指标/Judge 指标/未覆盖主题/可展开执行时间线）。
- API 层 `api/eval.ts`：全部报告/指标字段强类型定义（EvalReport/CaseResult/RuleMetrics/JudgeMetrics/CalibrationResult）。

## 15. LLM 可观测性与成本统计（observability）★

基于 **Spring AI 原生 Observation**（Micrometer）自动埋点，不引入 Langfuse/OTel（保留后续升级退路）；每次 LLM 调用落 `llm_trace` 表，按会话与 Agent 归因，前端观测台可视化。

### 15.1 采集链路

```
ChatModel 调用 → Spring AI Observation 自动触发
  → LlmTraceObservationHandler（ObservationHandler<ChatModelObservationContext>）
     onStart：记纳秒起点
     onStop：从 context 取 Prompt 全文/模型名/Usage/响应 → 组装 LlmTrace
     → 异步单线程 writer（ArrayBlockingQueue<Runnable>(1000) 任务队列，offer 失败丢弃+warn）
     → LlmTraceMapper.insert（评分回写同队列入队 update，保证晚于同轮 insert）
```

- 只捕获 ChatModel 层（`supportsContext` 泛型限定），`context.getError()` 非空记 status=error。
- **观测故障不影响面试主链路**：handler 内全 try-catch，写库异步且限流。
- **为什么 trace 里没有工具调用**：全仓未使用 LLM function calling（无 `@Tool`/`ToolCallback`）——编排是确定性 StateGraph，LLM 只负责内容生成，不负责行动决策；`AskQuestionTool` 名字带 Tool 但只是普通 Spring Bean，由图节点直接 Java 调用。ChatModel 层 Observation 天然只有 request/response/usage，因此数据模型就是扁平的单次调用行，**没有 tool span 是架构决定的，不是遗漏**。
- Prompt/回复**默认存全文**（`observability.prompt-excerpt-length` 默认 -1），受 12000 字硬上限保护（列类型 TEXT，防写入失败）；配置为正整数则截断到该字数。

### 15.2 归因、轮次 traceId 与跨线程传播（核心设计）

`LlmTraceContext`（sessionId + agent + roundTraceId）存 ThreadLocal（`LlmTraceContextHolder`），传播要点：

1. **LlmCallWrapper 临时 executor**：每次调用新建单线程执行 → submit 前捕获当前上下文快照并叠加 agent，在执行 callable 内 set、finally clear（收口点唯一，只改 wrapper 一处）；
2. **StateGraph 节点线程池**：所有节点包 `withTraceContext(NodeAction)`，在节点线程内从 `InterviewState` 取 sessionId + roundTraceId 设置（见 02 文档 2.1）；InterviewService 异步块（startInterview/resumeCoding）同样手动 set/clear，覆盖图外的计划/报告生成调用。
3. **轮次 traceId 串联**：`CoordinatorNode` 每次派发新题时生成 `rt-<12位随机>` 写入 `InterviewState.roundTraceId`，并**立即刷新当前线程上下文**（`withTraceContext` 在节点体执行前已用旧 state 设置，不刷新则本节点出题/检索会拿到上一轮 ID）；同轮的出题、检索、评分、追问 trace 行共享该 ID，追问轮不经过 Coordinator（followUp → evaluate）自然沿用主轮 ID。
- agent 归因名：plan / technical / project / coding / evaluator / followup / summarizer / testcase / code-eval / **retriever（知识库检索 span）**。

### 15.3 成本计算与清理

- 写入时按 `observability.cost` 单价计算 `estimated_cost`（默认 input 0.0024 / output 0.0096 元每千 token）；重试产生的多次调用各自成行均计入（token 真实消耗）。
- `observability.retention-days`（默认 30）控制保留期，`ObservabilityService` 提供过期清理。

### 15.4 检索 span 与评分回写

- **检索 span**：`KnowledgeRetriever.search` 三个出口（无结果/成功/异常）均落一条 `kind='retrieval'` 行（agent=retriever，promptExcerpt=`[kbId=X, topK] query`，completionExcerpt=`命中 N 个片段`，token/成本恒 0），可观测检索命中率与耗时；汇总统计（sessions/summary）只统计 `kind='llm'` 行，检索行不污染 token/成本口径。
- **评分回写**：`EvaluateNode` 评分完成后按当前轮 traceId 提交异步 update（`eval_score` 列），观测台抽屉直接展示本轮调整分（≥60 绿 / <60 黄）。

### 15.5 查询接口与前端

- `/api/observability/sessions?limit=`（会话维度汇总）、`/traces?sessionId=`（单场面试调用明细，时间升序）、`/summary?days=`（汇总统计：总 token/成本/错误数 + 按 agent 维度拆分，默认近 7 天）。
- 前端 `ObservabilityView`（路由 `/observability`，首页导航与快捷卡片双入口）：概览卡片（调用数/Token/估算成本/会话数）+ Agent 拆分表 + 会话汇总表 + 抽屉展开单会话每次调用详情（状态/耗时/成本/Prompt 全文与回复、检索 span 徽标、evalScore、轮次链路 traceId，`<details>` 折叠）。

### 15.6 与主流 LLM 可观测方案的差距对照

对标 LangSmith / Langfuse / Arize Phoenix / Helicone / OpenTelemetry GenAI 语义约定（`gen_ai.*`）：

| 维度 | 主流方案 | 本项目现状 |
|:---|:---|:---|
| 层级结构 | session → trace（一次业务请求）→ span 树（LLM/检索/工具/图节点） | ⚠️ 已有轮次级 traceId 串联同轮 LLM/检索行（非完整 span 树，无图节点层） |
| 消息明细 | 完整 messages 数组，按 system/user/assistant/tool 分角色 | ⚠️ 有全文摘录但无角色结构 |
| 工具调用 | 工具名/入参/出参/耗时/失败原因 | ❌（架构上未用 function calling，见 15.1） |
| RAG 检索 | query/召回片段/相似度分 | ✅ 已落 kind=retrieval span（query/命中数/耗时，无逐片段相似度分） |
| 流式指标 | TTFT（首 token 延迟）、生成速率 | ❌ |
| 重试链关联 | 重试串成同一 span/trace | ⚠️ 重试落多行，同轮共享 traceId 但无重试序号 |
| 评测绑定 | LLM-as-Judge 分数/用户反馈挂到 trace | ✅ 已按 traceId 回写 eval_score |
| Prompt 版本管理 | 模板版本化、A/B | ❌ |

剩余升级方向：图节点级 span 树、TTFT 流式指标、重试序号关联、Prompt 版本化（见 06 文档未来方向表）。

## 16. 结构化输出策略与解析容错 ★

系统不依赖模型层强制结构化，采用“prompt 约束 + 防御性解析 + 业务兜底”三层策略：

| 调用点 | 约束方式 | 解析与失败处理 |
|:---|:---|:---|
| PlanGenerator | `.call().entity(InterviewPlan.class)`（Spring AI `BeanOutputConverter` 自动注入 JSON Schema instruction） | Jackson 反序列化；空计划抛异常 → wrapper 重试 → 硬编码 fallbackPlan |
| AnswerEvaluator | prompt 声明“只输出 JSON” | 取第一个 `{` 到最后一个 `}` 子串解析；字段 `asInt(60)` 默认值兜底；**解析失败主动抛异常** → 重试 → 降级参考分 60 |
| TestCaseGenerator | prompt 声明 JSON 数组格式 | 剥离 ```json 包裹后 Jackson 解析；**失败返回空列表**（不注入假用例，避免拉低真实分数） |
| Technical/Project/CodingAgent 出题、FollowUpGenerator 追问 | 纯文本输出 | 不涉及 JSON |

- **当前缺口**：未使用模型层强制手段——DashScope 支持 `response_format: {"type": "json_object"}`（JSON 模式，解码层保证合法 JSON，可经 Spring AI `ChatOptions` 传入）与 JSON Schema 强约束（qwen 系列部分支持），可作为结构化可靠性的升级方向。
- **取舍说明**：降级分 60 / 空用例列表属于“保流程优先”的工程取舍，代价是轻微污染评估数据（与第 12 节缺口同源）。
